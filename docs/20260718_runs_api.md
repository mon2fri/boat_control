# Comparison and Validation Execution API

## Endpoint

### `POST /api/runs/execute/`

Executes comparison and validation on two CSV files.

**Request:**
```json
{
  "session_id": "abc123def456",
  "comparison_columns": ["id", "name", "status", "score"],
  "target_columns": ["score", "status"],
  "key_columns": ["id"],
  "filters": [
    {"column": "status", "operator": "eq", "filter_value": "active"}
  ],
  "rule_ids": ["R001", "R002"],
  "as_of_date": "2026-10-30",
  "commentary_template_columns": ["SEGMENT", "SCORE"],
  "new_exceptions_only": true
}
```

`commentary_template_columns` is the ordered Extra Columns for Commentary
Template selection. It is independent of `exception_columns`, rule extra
columns and comparison sections. `new_exceptions_only` defaults to `true` and
filters the response to `New` + `NotCommented`; all exceptions are still captured
and persisted. See
`docs/20261103_exception_tracking_template_optimization_run_report_contract.md`.

`session_id` references the server-side upload session. `as_of_date` is an
optional strict ISO calendar date. When omitted, the date retained by the upload
session is used, then the backend default (the last Monday-Friday of the previous
month). Invalid dates return HTTP 400 and never silently fall back.

**Response (200):**
```json
{
  "run_id": "abc123def456",
  "report_name": "file_a_vs_file_b",
  "created_at": "2026-10-30T12:00:00+00:00",
  "as_of_date": "2026-10-30",
  "result": {
    "comparison": {
      "total_rows_a": 120000,
      "total_rows_b": 120000,
      "rows_with_changes": 1500,
      "total_attribute_changes": 3200,
      "row_details": [
        {
          "row_index": 42,
          "key_columns": {"id": "12345"},
          "attribute_changes": [
            {"column": "score", "file_a_value": "10", "file_b_value": "15"}
          ],
          "change_count": 1
        }
      ]
    },
    "validation": {
      "total_violations": 50,
      "violations_by_rule": {
        "R001": [
          {
            "row_index": 10,
            "rule_id": "R001",
            "rule_identifier": "CBR1_00000000000000000000",
            "rule_name": "Active Check",
            "key_columns": {"id": "100"},
            "details": "Violated R001: Active Check"
          }
        ]
      },
      "violation_count_by_rule": {"R001": 50}
    },
    "rule_bindings": {
      "R001": "CBR1_00000000000000000000",
      "R002": "CBR1_11111111111111111111"
    },
    "common_columns": ["id", "name", "status", "score"],
    "target_columns": ["score", "status"],
    "filters_applied": [
      {"column": "status", "operator": "eq", "filter_value": "active"}
    ]
  }
}
```

Every successful run captures its exceptions into the separate tracking database
before the run document is written. Capture failure returns HTTP 500 with
`tracking_failed: true`, `retryable: true`, and the selected `as_of_date`; no run
is saved. Retrying the same date is idempotent. See
`docs/20261103_exception_tracking_run_capture.md` for identity, empty-run, and
crash-window details.

New results also include `commentary_template_columns` and
`new_exceptions_only`. The `new_exceptions_only` response view retains `New` and
`NotCommented` exceptions and hides `Commented` ones; the saved run still holds
every exception. `GET /api/runs/<run_id>/` and the export endpoints accept a
`new_exceptions_only` override.

New run results retain local `rule_id` values for grouping and add the canonical
`rule_identifier` to violations and rule summaries. `rule_bindings` records every
selected rule, including selected rules with zero violations. An explicitly empty
selection produces an empty binding map and does not mean all rules.

Legacy saved runs may omit these fields. Load compatibility supplies an empty
`rule_bindings` map and leaves unavailable canonical identities absent; it never
guesses an identity from an old `Rxxx` value.

## Processing Logic

### Comparison

1. Joins both DataFrames on the first common column (key)
2. Compares target columns row-by-row
3. Reports attribute changes with original values
4. Uses full outer join to catch rows unique to either file

### Validation

1. Loads all rules (or specified rule IDs)
2. Checks each row against rule conditions and logic
3. Reports violations with row index and key columns
4. Supports operators: eq, neq, contains, ncontains, gt, lt, gte, lte

### Filter Application

Filters are applied before comparison/validation:
- `eq`: Exact match
- `neq`: Not equal
- `contains`: String contains
- `ncontains`: String does not contain

## Performance

- Uses Polars lazy evaluation for initial filtering
- Materializes DataFrames only for comparison/validation
- Suitable for 120k x 200 datasets
- Deterministic results for same inputs
