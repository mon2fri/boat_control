# Validation Rule Catalog API

The SQLite catalog is live application storage. YAML/JSON files are portable configuration
documents and are read only by explicit migration/import operations.

## Catalog

`GET /api/rules/` returns the first 50 non-archived catalog rules plus all enabled rules outside
that slice. The response includes `enabled`, `rule_identifier`, `total`, `revision`, `has_more`,
`next_cursor`, and `pinned_rule_ids`. A cursor request reads at most 10 additional non-pinned
catalog rows. Cursors are revision-bound; a stale cursor returns `409` and the client must reload
the first page.

`POST /api/rules/` creates and enables a rule immediately. Drafts must not contain a client-selected
`rule_id` or `rule_identifier`.

`GET /api/rules/<rule_id>/` returns a local catalog record. `PUT` updates it. Presentation-only
changes retain the local ID and canonical identifier. Business-logic changes preserve the old
record disabled and return `previous_rule_id` plus the resulting record. `DELETE` soft-archives
and disables the record; it does not remove identity or historical data.

`POST /api/rules/enablement/` accepts `{ "rule_ids": ["R001"], "enabled": true }` or `false`.
Bulk changes are atomic and use explicit local IDs. An empty enabled set is valid.

`POST /api/rules/reorder/` changes the order of the explicit enabled IDs without changing catalog
positions or identifiers.

## Configuration Import/Export

`POST /api/rules/configs/` writes a named export containing exactly the currently enabled catalog
rules, queried directly from SQLite. The exported entries contain complete authored rule payloads
and `rule_identifier`; disabled and archived rules are omitted. An empty enabled set exports a
valid empty rules array.

`POST /api/rules/configs/import/` accepts `{ "rules": [...] }` and validates the complete document
before the database transaction. It recalculates identities, rejects duplicate canonical rules and
mismatching diagnostic identifiers, reuses matching catalog rows, imports missing rows, enables the
provided order, and disables omitted non-archived rows without deleting them. The response includes
`imported`, `reused`, `enabled`, and `bindings`.

The named detail `PUT /api/rules/configs/<name>/` applies the same import behavior and updates the
named document only after a successful catalog operation. Invalid input or a failed transaction
leaves catalog state unchanged.

## Migration and Operations

After Django migrations, run:

```text
python backend/manage.py migrate_rules_to_db
```

The command validates and imports the legacy active rules file once, preserves legacy `Rxxx` IDs,
order, and `next_index`, enables migrated rules, and leaves the source file untouched. It is
idempotent after `RuleStoreState.initialized` becomes true, including for an intentionally empty or
fully disabled catalog. Both `scripts/dev.sh` and `trigger.py` invoke it after `migrate`.

`Rxxx` is a local operational ID. `CBR1_...` is the stable canonical business-rule identifier;
clients receive it read-only and must not use it as the CRUD route key in this phase.
